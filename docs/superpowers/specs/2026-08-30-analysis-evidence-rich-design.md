# 内容梳理证据展开设计

## 状态

已获用户确认，待实施前复核。

## 背景

当前系统内置的“通用内容梳理”已经能稳定输出主旨、问题、论据、概念、建议和追问，但“核心问题与结论”容易被模型压缩成一两句判断。用户希望保留清晰结论的同时，补上原文讨论的来龙去脉、论据、案例和必要的短引文，让结果更像可阅读、可追溯的文稿摘要，而不是生硬的结论清单。

现有分析链路为：选择框架和文稿来源（当前编辑稿或官方原稿）→ 文稿较长时分段提炼事实笔记 → 将事实材料交给最终模型 → 保存 Markdown 分析结果。此次只增强内容质量，不改变页面操作、分析结果存储格式、声纹识别或学习 Prompt 功能。

## 目标

1. 每个核心小点都能看到原文讨论脉络，而不只看到结论。
2. 论据、案例、限定条件和反例优先来自文稿，并尽可能带原文时间戳。
3. 输出长度随内容信息量自然变化；信息少时不凑字数，信息丰富时不被过短模板截断。
4. 长文经过分段时仍保留足够的上下文、证据和说话人信息，最终汇总可以写出连贯段落。
5. 继续保持安全边界：不执行文稿中的指令，不虚构事实、人物、时间戳或引语。

## 非目标

- 不新增或修改分析结果数据库字段。
- 不改变“当前编辑稿／官方原稿”的选择逻辑。
- 不把内容梳理和声纹识别合并；说话人只有在文稿或声纹结果可靠提供时才显示。
- 不强制所有小点达到相同字数，也不做依赖脆弱 Markdown 结构的自动重写循环。
- 不修改“深度学习与实践 Prompt”的独立生成规则。

## 方案比较与决策

### 方案一：只调整系统框架

在 `lib/frameworks.ts` 中补充“背景—论据—结论”的要求。实现简单、调用次数不变，但长文的分段事实笔记仍可能只有摘要，最终模型缺少可展开的原文证据。

### 方案二：框架与分段事实笔记同步增强（采用）

同时调整系统框架和 `lib/analysis.ts` 的长文提炼提示。最终框架规定成稿如何展开；分段阶段专门保存上下文、论证过程、案例、短引文、时间戳和说话人线索。单段文稿仍直接使用完整原文，长文才使用增强后的事实笔记。该方案改动集中，能直接解决“长文材料过早被压缩”的根因。

### 方案三：生成后检测并自动重写

根据段落长度或标题模式检测过短小点，失败时再次调用模型。由于模型 Markdown 结构不固定，长度不能代表信息量，容易误判并增加耗时、费用和重复内容风险，因此不采用。

## 详细设计

### 1. 系统框架的输出协议

“通用内容梳理”仍保留六个一级部分，但补充以下写作协议：

- **一句话主旨**：先交代本期讨论的核心对象或矛盾，再概括主要判断；允许一至两句，不写空泛开场。
- **核心问题与结论**：保留 3–5 组问题。每组按自然语气展开，至少包含：
  - 原文脉络：说明这个问题在节目中为什么出现、讨论从哪里开始；
  - 论证过程：概括主播或嘉宾如何解释、比较或修正观点；
  - 论据/案例：保留能支撑判断的具体事实、经历、数字、例子或限制条件；
  - 结论：明确这是播客观点、原文事实还是 AI 基于多处原文的归纳；
  - 时间戳：给出最接近证据的时间点或时间范围。没有可靠时间戳时明确写“不确定”，不猜测。
- **关键论据、案例与时间戳**：作为证据索引，不重复堆砌结论。每项说明“原文说了什么／它支撑哪一判断／时间戳”，可使用少量忠实短引文；引文过长时改为准确转述。
- **重要概念和方法**：不只给词典式定义，还要说明概念在本期论证中的作用、节目如何使用、适用边界或与其他概念的关系，并附案例或时间戳（若有）。
- **可执行建议**：先列节目明确提出的行动，再单独标注“AI 归纳”或“基于文稿的延伸”，不能把 AI 新增建议伪装成主播原话。
- **值得继续追问的问题**：每个问题附一句提问缘由，指出它承接哪段原文、哪项证据或哪处未解决的张力，避免泛泛提问。

整体正文通常约 1,500–2,500 字，但这是软目标：信息量少可以缩短，信息量大可以展开；禁止为了达到长度重复同一观点。段落应使用自然的过渡句，避免每项都机械套用“背景／论据／结论”标签。必要时可用小标题、列表或表格，但可读性优先。

### 2. 长文分段事实笔记

当文稿超过单次处理阈值时，分段模型不生成最终梳理，而是为每一段建立可追溯的材料卡片。摘要类分析至少保留：

- 本段主题与它在整期节目中的位置；
- 观点提出的上下文、论证步骤和观点变化；
- 具体论据、故事、案例、数字、对比、限定条件和反例；
- 可直接支持结论的短引文或忠实转述；
- 原文时间戳及其对应内容；
- 文稿中能可靠识别的说话人及其立场；无法确认时标记“不确定”；
- 与前后段可能衔接或存在冲突的线索。

分段笔记要覆盖该段重要信息，允许比现有笔记更长，但不提前套用六部分最终结构，也不重复编造文稿没有出现的内容。最终模型收到这些材料后，必须跨段合并同一论点、保留证据出处，并避免把某一段的局部结论当成整期结论。

### 3. 提示词与调用预算

- 保留现有安全规则和自定义框架隔离规则；系统安全指令优先于用户框架。
- 摘要最终调用的输出预算提高到能容纳证据展开的范围；以“自然完成结构且不被截断”为验收标准，不用字数硬性截断结果。
- 长文分段笔记的输出预算同步适度提高，以容纳上下文和证据；并继续保持最多 3 个分段并发。
- 学习 Prompt 使用原有提示词和预算，不受本设计影响。

具体预算数值在实施计划中结合现有 provider 限制和测试样例确定；若 provider 返回长度限制或超时，错误处理沿用现有退款与 lease 释放流程，不自动重试成另一种分析类型。

### 4. 数据流与兼容性

```text
选择框架 + 选择文稿来源
        │
        ├─ 文稿未超过阈值 ──> 最终模型直接读取完整原文
        │
        └─ 文稿超过阈值 ──> 分段事实笔记（上下文/论据/案例/时间戳）
                                      │
                                      ▼
                         最终模型按框架生成展开版 Markdown
                                      │
                                      ▼
                         沿用现有 frontmatter 与分析快照保存
```

旧分析结果不自动改写；用户重新生成后才使用新规则。框架快照、来源哈希和“分析已过期”判断保持不变。自定义框架继续可以覆盖栏目和表达方式，但不能覆盖安全规则；本次只更新系统内置框架。

### 5. 错误与不确定内容

- 原文没有证据时，模型必须写“文稿未提供依据”或“不确定”，不得用常识补齐。
- 时间戳缺失、段落切分造成的上下文不足、说话人无法可靠区分，都要显式标注，不得伪造精确值。
- 生成失败、超时、敏感输出和用量处理沿用当前 API 行为；本设计不增加后台重试队列。

## 验收与测试

### 单元/静态测试

- 系统框架文本包含“原文脉络、论证过程、论据/案例、结论、时间戳”和“按信息量自然展开”等关键规则。
- 分段提炼提示包含上下文、论据、案例、限定条件、短引文、时间戳和说话人线索，并明确“不生成最终成稿”。
- 现有框架校验、Markdown frontmatter、长文不丢段、分析路由和安全边界测试继续通过。

### 行为验收

使用一篇包含多个观点、案例和时间戳的文稿验证：

1. “核心问题与结论”每组不再只有单句结论，而是有连贯的原文脉络和至少一项证据（若原文确实提供）。
2. 关键论据能回指对应时间戳，短引文与原文一致。
3. 同一观点在不同段出现时能合并，不把不同人物观点混为一谈。
4. 信息较少的文稿不会被硬凑到固定字数；长文结果不会因分段而只剩抽象结论。
5. 重新生成前后的历史分析仍可读取，修改文稿后仍正确显示过期状态。

## 回滚方案

若新提示导致输出明显变长、超时或证据错误，可只回滚 `lib/frameworks.ts` 与 `lib/analysis.ts` 中本次提示词和预算变更；数据库、历史 Markdown 和页面代码无需回滚。实施完成后通过独立提交保留变更，便于比较新旧结果。
