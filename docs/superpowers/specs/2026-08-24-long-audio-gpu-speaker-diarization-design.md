# 长音频 GPU 说话人识别设计

## 目标

将本地说话人识别从当前的 30 分钟、500MB 验证上限扩展到首期 2 小时、1GB，并在检测到 CUDA 时优先使用 GPU；同时保证 2GB 显存不足时仍能自动回退到 CPU。

## 已知约束

- 当前工作树为 `feature/audio-speaker-diarization`，本地服务只监听回环地址。
- 当前电脑检测到 NVIDIA GeForce MX450，2GB 显存，驱动报告 CUDA 12.8。
- 虚拟环境当前安装的是 `torch 2.11.0+cpu`，因此必须补装 CUDA 版 PyTorch 才能真正使用 GPU。
- 当前 pyannote pipeline 一次接收整个音频；长任务的进度会长时间停留在同一个百分比，且没有分块失败恢复。
- 音频文件不会上传到云端；分块仍在本地服务内完成。

## 方案

### 1. 长音频分块

- 浏览器和服务端共同使用 `MAX_DURATION_MS = 2 * 60 * 60 * 1000` 与 `MAX_BYTES = 1 * 1024 * 1024 * 1024`。
- 引擎使用 10 分钟核心窗口与 15 秒前后重叠。
- 通过 `torchcodec.AudioDecoder.get_samples_played_in_range` 按时间范围读取音频，避免将 2～3 小时原始音频一次性加载到内存。
- 每个分块的输出转换为绝对时间，裁剪到核心窗口后再合并，避免重叠区域重复写入。
- 分块之间按重叠区的时间交集匹配匿名说话人；无足够交集时创建新的匿名 ID，并在前端保留人工确认能力。这样不声称获得声纹级身份确认。
- 每完成一块更新任务进度；取消任务在块边界生效，已完成块不再继续计算。

### 2. GPU 设备策略

- `SPEAKER_DEVICE=auto` 为默认值：CUDA 可用时将 pipeline 移到 CUDA，否则使用 CPU。
- `SPEAKER_DEVICE=cpu` 强制 CPU；`SPEAKER_DEVICE=cuda` 请求 CUDA，但 CUDA 不可用或显存不足时安全回退 CPU并记录状态。
- 安装脚本检测 `nvidia-smi`，有 NVIDIA GPU 时使用 CUDA 版 PyTorch wheel；无 GPU 时继续使用 CPU wheel。
- 健康检查返回实际设备（`cuda` 或 `cpu`），但不返回路径、Token 或个人信息。

### 3. 前端行为

- 更新文件大小/时长提示为 2 小时、1GB。
- 进度文案明确显示“正在处理第 N/M 块”，避免长时间无反馈。
- 保持现有预览、说话人标签修正和保存流程不变。

## 错误处理

- 超过 2 小时或 1GB：上传前和服务端均拒绝，不启动模型。
- 某个分块解码或推理失败：任务整体失败并清理临时目录，不返回不完整结果。
- CUDA 初始化失败或显存不足：本任务切换 CPU 继续处理；健康检查报告实际设备。
- 分块之间无法可靠匹配的说话人继续使用匿名编号，并由预览页标记待确认，不伪造身份。

## 验收标准

1. 现有 Python 与 TypeScript 测试全部通过。
2. 无 CUDA 时仍能完成当前 5 分钟测试音频识别。
3. 有 CUDA 版 PyTorch 时健康检查报告 `cuda`；CUDA 不可用时报告 `cpu`。
4. 分块引擎测试验证绝对时间、核心窗口裁剪、重叠匹配和进度回调。
5. 2 小时以内且不超过 1GB 的文件可进入任务；超限文件在页面和服务端均被拒绝。
6. 先用 5～10 分钟音频做真实回归，再用 30～60 分钟音频验证分块进度；不在没有实测的情况下宣称 3 小时性能。

## 非目标

- 本期不做跨单集声纹注册或说话人实名识别。
- 本期不把音频上传到 Worker、R2 或任何第三方 API。
- 本期不承诺 3 小时在 MX450 2GB 上一定使用 GPU；显存不足时允许回退 CPU。
